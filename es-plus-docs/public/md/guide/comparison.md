# 与其它方案对比

选型问题从来不是「谁更强」，而是「谁的边界落在你的工程里」。这一页只对比结构差异与可验证的数字，不裁断谁更好；每个对比对象都写清「它在哪比我们强」，因为不写那一段的对比文章不值得读。

> 口径说明：本文关于本项目的数字全部来自仓库内实测产物（`docs/brand/one-config-diff.json`、`docs/cases/cases-metrics.json`）与守卫脚本，日期 2026-10-28；关于外部项目的描述只写其公开定位与交付形态，不引用它们的版本号与性能数字（那些会过期，读者应以其官方文档为准）。

## 一张表看定位差异

| 方案 | 交付形态 | 与你的工程的耦合 | 覆盖范围 | 三端同一份配置 |
|---|---|---|---|---|
| ES-Plus | 组件库 + 配置 schema（JSON） | 装进现有 Vue 工程，按需局部使用 | 中后台 CRUD：表单 / 表格 / 弹窗 / 页面 | 是（Element Plus / Element UI / Ant Design Vue） |
| 原生手写 | 你自己的模板与事件处理 | 无 | 你写多少有多少 | 否 |
| vue-element-admin 一类后台模板 | 可克隆的后台工程模板 | 复制整个工程再改 | 后台外壳 + 若干页示例 | 否 |
| Formily | 表单领域的 schema 引擎 | 装进工程，专注表单 | 表单与字段联动（深） | 否（表单层，不产 CRUD 页面） |
| amis | 整页 JSON DSL + 配套平台 | 渲染器自成体系 | 整页低代码（含 CRUD） | 否（自带组件体系） |
| TypeChat | 自然语言 → 类型化 JSON 的库 | 嵌进你的服务或应用 | 意图 → 结构（不含渲染） | 否（不含渲染层） |

## vs 原生手写

原生写法的成本不在难，在**重复但不机械**：每个页面的字段、接口、状态机、校验、按钮权限都不同，复制粘贴每次要改几十处。

仓库里对同一功能的两种实现做了逐行实测（同一功能范围、无省略号、无 stub；`lines` 是整文件非空行，配置成本不藏）：

| 场景 | 原生 | ES-Plus | 行数变化 | 事件绑定 | 自写函数 | `v-if` 分支 |
|---|---|---|---|---|---|---|
| 查询 + 表格 + 分页 + 行内查看 | 123 行 | 77 行 | −37.4% | 7 → 1 | 6 → 2 | 2 → 0 |
| 码值列：中文标签 + 空值占位 | 36 行 | 43 行 | **+19.4%** | 0 → 0 | 1 → 0 | 3 → 0 |

第二行是刻意留着的反例：**小场景下配置比手写长**。用 `dataOptions` 写三个码值与空值占位，比在模板里写三条 `v-if` 多出几行 JSON；换来的是分支归零、码值集中。如果你的页面只有一列状态，原生写更快 —— 这不是营销话术能盖掉的事实。

另一组口径不同（模板 + 事件胶水代码，不含 script 里的数据结构）：

| 口径 | 原生 | ES-Plus | 降幅 |
|---|---|---|---|
| 模板 + 事件胶水代码 | 115 行 | 27 行 | −76.5% |
| 整页行数（含空行与数据） | 151 行 | 90 行 | −40.4% |

两个降幅差别这么大，是因为整页分母里还有 schema 本身。**只报 −76.5% 是不诚实的**，首页那个数字下面写着它的口径。实测脚本：`npm run one-config:gen`；对照页：[/native-vs-ai](/native-vs-ai)。

## vs vue-element-admin 一类后台模板

差在**交付形态**，不在功能。那类项目给你一整个可运行的后台（登录、布局、权限路由、若干示例页），你 clone 下来改成自己的；它的价值是「一周内跑起来」。要付出的是：后续每个业务页仍然手写，且模板与官方组件库的升级节奏不同步。

ES-Plus 是一个库，不提供后台外壳。已有的工程里局部换掉「表单 + 表格 + 弹窗」这一条链，其余部分照旧。如果你连登录页、路由守卫、布局都要从头搭，模板类项目仍然是更快的起点 —— 它不是竞品，是不同层次的东西。

## vs Formily

Formily 在**表单**这一层比 ES-Plus 深：更完整的字段协议、布局体系、自定义组件接入方式，适合把表单本身当产品做的团队。

ES-Plus 的边界是「表单 + 表格 + 弹窗」连起来的那条 CRUD 链：字段配置同时决定查询表单、表格列、弹窗表单三处的呈现（`inQuery` / `inTable` / `inForm` 三个开关），按钮权限与 i18n 覆盖三处，一台页面一份配置。字段联动用的是 `reactions`（JSON 表达式，不是回调），这一点与 Formily 的响应式思路同向。

如果你的页面里表单占九成、表格只是附属，Formily 更合适；如果一半工作量在表格与弹窗的连线与权限上，ES-Plus 的覆盖面更贴题。

## vs amis

amis 用 JSON 描述**整页**，带一整套自研组件与可视化搭建平台，适合「低代码平台」这个目标：给不懂前端的人配页面。

ES-Plus 不做平台，也不自带组件：它渲染在 Element Plus / Element UI / Ant Design Vue 上，这是三端同 schema 成立的前提，也意味着你的设计规范、主题、国际化都是组件库那一套，不需要第二套。代价是覆盖面窄 —— 只到 CRUD，不做任意布局编排。

## vs TypeChat

TypeChat 解决的是「自然语言 → 类型化 JSON」，强在把 LLM 的输出约束到你给的类型上，之后的事它不管。

ES-Plus 的 AI 部分（MCP Server、CLI `--ai`、确定性生成器）解决的是后半程：类型化配置如何变成**能编译、能跑、三端一致**的页面。两者不冲突：用 TypeChat 拿结构、用 ES-Plus 落地渲染，是一条可行的组合。反过来，只想用 LLM 省掉写配置这一步而不用它的渲染层，也可以 —— 但没有渲染层的约束，生成结果对不对就没人替你验。

## 什么场景不要选 ES-Plus

- **页面只有一两张表单**，没有表格与弹窗的连线：配置层带来的间接性大于收益。
- **需要任意布局编排**（仪表盘、可视化大屏）：CRUD 之外的布局不在这份 schema 的表达范围里。
- **不用 Element Plus / Element UI / Ant Design Vue**：渲染端绑定是刻意的，脱离这三者就没有「同一份配置」这回事。
- **团队不接受配置驱动**：配置文件成为代码评审的对象，这个习惯要么建立，要么别引入。
