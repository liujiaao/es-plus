# 别让 AI 瞎写前端：让 LLM 生成的 CRUD 页面可验证、可复现

> 一句话：**让 LLM 只写一份配置，把"生成正确代码"交给编译器。** 同一份配置，确定性编译出 Vue 3 + Element Plus / Vue 2 + Element UI / Vue 3 + Ant Design Vue 三套可运行代码，字节级可复现，CI 守着不漂。

## 一、AI 生成前端的真问题，不是"不会写"

2026 年，让大模型写一个 CRUD 页面已经不稀奇。你把需求丢给 Claude、Cursor、v0，它"唰"地吐出一屏能跑的代码。

稀奇的是——**你敢不敢把它直接合进代码库？**

多数人不敢，因为 AI codegen 是"凭感觉"的：

- **不确定**：同一句话问两遍，产出两份不一样的代码。今天能跑，明天重新生成就换了一套写法。
- **对不上设计系统**：它用的是它脑子里"平均互联网"的组件写法，不是你团队的 `EsTable`、不是你约定的字段映射、不是你的权限指令。
- **没人替它校验**：生成的 `prop` 拼错了、`formtype` 写了个不存在的值、分页事件漏了——没有任何东西在合并前拦下来。

于是你省下的那点"打字时间"，又在 **逐行 review → 改 → 再 review** 里还了回去。生成式的爽，败给了审查的累。

## 二、反直觉的分工：LLM 做语义，编译器做确定性

问题的根子在**边界划错了**。大家默认让 LLM 一路干到底——从"理解需求"一路干到"吐出最终代码"。但这两件事的性质完全相反：

| | 适合谁 | 要的是 |
|---|---|---|
| 把模糊需求变成结构化意图 | **LLM** 擅长 | 语义理解、容错、填空 |
| 把结构化意图变成正确代码 | **编译器** 擅长 | 确定性、可校验、可复现 |

LLM 的非确定性是**特性**，不是 bug——你恰恰需要它在"理解人话"这一端有弹性。但你**不该让这份弹性渗进"生成代码"那一端**。

ES-Plus 的做法就是把这条线划清楚：

> **LLM 只产出一份 JSON 配置；库负责校验这份配置，并确定性地编译成三端代码。**

LLM 碰不到最终代码的任何一个字符。它的输出是一份**声明式配置**——而配置能被 schema 校验、能被确定性编译。非确定性被关在了"理解需求"这一格里，出不来。

## 三、怎么做到的（每条都可当场验证，不是宣称）

### 1. MCP 把 Schema 和约定交给宿主 LLM

ES-Plus 配套一个 MCP Server。你在 Claude Code / Cursor 里接上它，宿主 LLM 就拿到了 ES-Plus 的配置 Schema、字段约定、golden 示例。你说"做一个订单管理页，带状态筛选和批量删除"，LLM 产出的不是 `.vue` 文件，而是一份结构化配置：

```jsonc
{
  "mode": "crud-page",
  "fields": [
    { "prop": "orderNo", "label": "订单号", "formtype": "Input" },
    { "prop": "status", "label": "状态", "formtype": "Select",
      "dataOptions": [{ "label": "待付款", "value": 0 }, { "label": "已完成", "value": 1 }] }
  ],
  "tableBtns": [{ "name": "批量删除", "type": "danger" }]
}
```

### 2. 库在编译前校验——坏配置到不了产物

这份配置先过一道 zod + JSON Schema 校验。非法的东西**在编译前**就被挡回去，而不是编译成一个带 bug 的页面让你上线后才发现：

- `formtype` 必须是 14 个合法控件之一（`Input`/`Select`/`DatePicker`/…）。LLM 幻觉出一个 `"dropdown"`？直接拒绝。
- `prop` 不许带路径分隔符、不许是 `__proto__`/`constructor`/`prototype`——它会变成生成文件的成员名和核心插槽名，含注入字符的直接拒绝。
- 必填项缺失（表格列没有 `prop`、弹窗没有 `title`）当场报错，带明细。

### 3. 确定性编译——同一份配置，字节级相同的三端代码

校验通过后，`generateFromConfig` 把这份配置编译成三套代码。关键词是**确定性**：同一份配置，无论跑多少次、在谁的机器上跑，产出**逐字节相同**。

这不是口号。它被一套反向探针守着：即使有人塞进 `width: "20' + (1) + '"` 这种注入载荷，编译器也只会把它当字符串转义，产物里**不会**出现可执行的注入串——`check:generator-escaping` 这道守卫用恶意配置天天在 CI 里验证这一点。

### 4. 守卫背书——可验证性是被强制的，不是被声称的

别的库说"我们很可靠"是 PPT；ES-Plus 的可靠性是 **CI 里天天在跑的断言**：

- **25 个 golden 用例** × 多类确定性不变量，每类都包含 **esbuild 真语法解析**——产物不是"看起来像代码"，是"真能被解析成 AST 的代码"。
- **32 道一致性守卫**连成一条链：类型三端同构导出、schema 单源、契约消费、三端渲染对等……任何一端悄悄发散，CI 当场红。

这是 ES-Plus 和"又一个 AI codegen 玩具"最大的区别：**它把"生成的东西可信"这件事，做成了可执行、可复现、持续验证的工程契约。**

## 五、诚实的边界

不吹，反而更可信：

- **它不是"生成任意 UI"**。它专注 CRUD 全链路——表单查询、表格展示、弹窗编辑。要做一个官网落地页、一个数据大屏，这不是它的场景。
- **非标需求有逃生舱**。配置覆盖不到的地方，`render` 字段让你写原生 JSX/模板，不被声明式框死。
- **三端一致 ≠ 三端像素级相同**。Element 和 Ant Design 的设计语言不同，ES-Plus 保证的是**行为与结构一致**，不是让 Ant 的按钮长得跟 Element 一样。

## 六、三步上手

```bash
# 1. 装渲染器（以 Vue 3 + Element Plus 为例）
npm install @es-plus/vue3 element-plus @element-plus/icons-vue

# 2. 接上 MCP Server（在 Claude Code / Cursor 的 MCP 配置里加 @es-plus/mcp-server）

# 3. 对着 AI 说："用 es-plus 做一个订单管理 CRUD 页"
```
